ArkaOS documentation

A privacy-first, immutable desktop Linux — how it's built, what it enforces, and how to run it.

ArkaOS closes the "GrapheneOS-for-desktop" gap: a desktop OS that is private and tamper-resistant by default, without asking the user to configure any of it. The whole system is one verified container image — read-only at runtime, atomic to update. This is Developer Preview 1 (DP1): it targets QEMU/KVM and is built from source; there is no hardware installer yet, by design.

Introduction

ArkaOS is built on the bootc immutable image model. Instead of a package manager mutating a live system over time, the entire OS is declared in a single Containerfile, built into an OCI image, and deployed as an atomically-updated, read-only root filesystem. The machine you boot is byte-for-byte the image you built — no configuration drift, and a bad update rolls back to the exact previous state.

Two things are protected, by two components:

ComponentProtectsHow
arkadThe personContinuously enforces network-privacy invariants (MAC, DNS, hostname, IPv6).
Immutable baseThe machineRead-only composefs root, atomic bootc updates, rollback.
i

Honesty over marketing is a core project value. Everything in these docs describes what a booted image actually does; where something is designed but not yet proven, it says so.

Architecture

The build is a multi-stage container image:

  • Stage 1 — rust:alpine: compiles arkad as a static musl binary (x86_64-unknown-linux-musl), so it has no runtime library dependencies.
  • Stage 2 — fedora-bootc:42: installs the arkad binary and its systemd unit, the branded KDE Plasma desktop, and the sandboxed Firefox.

At runtime the layers stack like this — the person at the top, hardware at the bottom, with arkad as the privacy layer in the middle:

LayerWhat it is
Youthe person
Arka ShellKDE Plasma, branded — dock, top bar, first-boot wizard
ApplicationsFirefox (bubblewrap), Capsule
arkadprivacy daemon — Rust, static musl
Immutable basebootc + composefs, read-only
Linux kernelfedora-bootc 42
Hardwarebare metal / VM

arka is Sanskrit for ray of light: the daemon at the center of the stack keeps that light yours.

Privacy daemon — arkad

arkad is a small Rust daemon that enforces privacy invariants and keeps them enforced. It runs four independent enforcers:

EnforcerWhat it doesWhere
mac.rsRandomizes the hardware (MAC) address per connectionNetworkManager conf.d
dns.rsForces DNS-over-TLS to Quad9 (9.9.9.9)resolved.conf.d
hostname.rsMasks the hostname to a generic arkahostnamectl
ipv6.rsEnables IPv6 privacy (temporary) addressesuse_tempaddr = 2

The main loop enforces all four on start, then re-verifies every 60 seconds and re-enforces on drift. It deliberately uses no async runtime (thread::sleep, not tokio) and no nix crate — every change is made through well-known CLI tools (nmcli, hostnamectl, sysctl). Configuration lives at /etc/arkad/arkad.toml, with secure defaults baked in so it works correctly with no config file at all.

i

arkad does not use D-Bus to enforce these invariants — it calls the same tools an administrator would, which keeps its surface small and auditable.

Browser sandbox

Firefox runs inside a bubblewrap sandbox. /usr/bin/firefox is a symlink to a wrapper; the real binary lives at /usr/bin/firefox-unwrapped. The wrapper is baked in at build time, and composefs locks it read-only at runtime.

Inside the sandbox:

  • Your real /home is hidden behind a tmpfs — the browser sees an empty home.
  • /etc is an allowlist — no NetworkManager credentials, no arkad config, no machine-id.
  • /run is a tmpfs — no host D-Bus.
  • Only ~/Downloads is bound back in, so downloads still work.
✓

Verified in a booted image: a sentinel file in the real home is unreadable inside the sandbox, and /etc/NetworkManager and /etc/arkad are absent.

Boot & integrity

The root filesystem is a read-only composefs overlay backed by an ostree object store — structural immutability, so the running system cannot be modified in place.

For measured boot, ArkaOS uses the TPM: PCRs 0–10 are measured and verified (via swtpm in a VM, real TPM on hardware). Full measured boot through PCRs 11–15 requires a signed UKI + systemd-boot as the active boot path, which is not yet wired up — GRUB remains the active bootloader today.

!

Known limitation. PCR 11–15 measured boot and full-disk encryption are not in DP1. FDE (TPM-sealed LUKS) is required before 1.0 — a stolen disk reading clean would contradict the whole premise — and needs real hardware to prove.

Building from source

The build runs inside a rootful podman-bootc machine (qemu), which virtiofs-mounts your home at /var/home. Prerequisites: an Arch Linux host with podman and a running podman-machine-default.

1 — Build the image

shell
podman machine ssh podman-machine-default \
  "podman build --pull=newer -t localhost/arkaos:dev /var/home/Ram/arkaos/"

2 — Produce a bootable qcow2

Feed the image to bootc-image-builder. It needs the host container storage bind-mounted, and writes a disk.qcow2 into output/.

shell
podman machine ssh podman-machine-default \
  "podman run --rm --privileged \
    -v /var/lib/containers/storage:/var/lib/containers/storage \
    -v .../config.toml:/config.toml:ro \
    -v .../output:/output \
    quay.io/centos-bootc/bootc-image-builder:latest \
    --type qcow2 --rootfs xfs localhost/arkaos:dev"
i

Kill any boot-test VMs before running the image builder — two QEMU VMs plus a build will exhaust memory and the podman machine dies. And never prune between the build and the builder: it can delete the freshly-tagged image.

Booting DP1

Boot the qcow2 under QEMU/KVM. Two details matter: use Fedora's OVMF firmware (Arch's edk2 crashes Fedora's GRUB), and use virtio-vga (not virtio-gpu, which leaves the display output inactive).

shell
# fresh copy of the OVMF vars each boot
cp OVMF_VARS_4M_f42.qcow2 OVMF_VARS_4M_f42_boot.qcow2

qemu-system-x86_64 -enable-kvm -m 4096 -cpu host -smp 2 -machine q35 \
  -drive if=pflash,format=qcow2,readonly=on,file=OVMF_CODE_4M_f42.qcow2 \
  -drive if=pflash,format=qcow2,file=OVMF_VARS_4M_f42_boot.qcow2 \
  -drive file=output/qcow2/disk.qcow2,format=qcow2,if=virtio \
  -device virtio-vga -display gtk -usb -device usb-tablet \
  -serial telnet::4445,server,nowait -monitor telnet::4444,server,nowait

On first boot, the wizard creates your user account. Pick any username and a password of at least 8 characters. After that, autologin takes you straight to the KDE Plasma desktop; a serial console is available at telnet localhost 4445.

Threat model

What ArkaOS defends against today, and what it does not — stated plainly.

ConcernStatus
Network-level identity & tracking (MAC, DNS snooping, hostname leak, IPv6 correlation)defended arkad enforcers
Configuration drift & in-place tampering of the OSdefended read-only composefs root
Browser reading your files / system secretsdefended bubblewrap sandbox
Boot-chain measurement (early PCRs)partial PCR 0–10
Data-at-rest on a stolen disknot yet FDE planned before 1.0
Full measured boot (UKI, PCR 11–15)not yet needs signed boot path

Status & roadmap

DP1 is a developer preview, verified in a VM. Honest readiness: engineering ~9/10, product ~4/10 — the engineering is mature for a preview; the uncertainty is deployment and hardware.

  • Shipping: immutable base, arkad, browser sandbox, KDE Plasma desktop — all verified booting.
  • Target: QEMU/KVM, delivered as a qcow2 built from source; no installer.
  • Next: real hardware (drivers, suspend), full-disk encryption, a live-ISO installer, and full measured boot.

Scope for the next release is decided from real daily-driving experience, not a wishlist — see FUTURE-CONSIDERATIONS.md and FIELD-NOTES.md.
